# PR #12 review against main

PR: https://github.com/gecko-of-shadow/twitch-adblock/pull/12 (`perf-and-race-fixes`, head `3a927d4`).
Main: `938699e` (#16), which is newer than `0a5e7c0` (#17).
Reviewed 2026-10-29 UTC. I rebased locally only: nothing was pushed, merged, commented or labelled.

## Verdict

Not mergeable as it stands. Rebased onto main it has 2 small text conflicts, which are easy to fix,
and 3 test failures from #17's new test file. Two of those failures come from limits in the test's
fake Chrome, not from bugs in #12. The third is a real policy clash: #12 adds `unlimitedStorage` and
`alarms`, and main checks in 6 places that no such permission is added.

Neither permission is needed:

- **`unlimitedStorage`:** I measured the real stored data at 6.87 MiB of the 10 MiB quota.
- **`alarms`:** #12's first commit already lets a refresh that Chrome cut off pick up where it stopped.

The rest of #12 is sound and worth landing: per-list saves, the swap using the lists in memory,
no storage watch in pages, smaller `cosMeta`, and the release-gate required-files check.

## Are `unlimitedStorage` and `alarms` needed?

Short answer: no. Each one can be avoided, and main currently forbids both.

### `unlimitedStorage`: not needed today

I ran #12's real `GU.refresh` (from `src/general/update.js`) against the live lists with an
in-memory `storage.local`, and measured the JSON bytes it stores. Live list fetch on 2026-10-29,
all 9 lists OK. Script: `measure.mjs` in the session scratchpad (not committed).

| What is stored | Size |
| --- | --- |
| `generalListRefresh` (9 lists: domains, plus parsed cosmetic data for EasyList) | 5.93 MiB |
| — largest list: `hagezi_pro_mini`, 87,995 domains | 1.83 MiB |
| — `easyprivacy` | 1.05 MiB |
| — `easylist`: domains 0.88 MiB + cosmetic 0.77 MiB | 1.65 MiB |
| Cosmetic keys (`cosG`, `cosS:*`, `cosE:*`, `cosMeta`, `cosKeys`; 8,339 keys) | 0.95 MiB |
| **Total** | **6.87 MiB of the 10 MiB `storage.local` quota** (Chrome 114+) |

- About 3.1 MiB is left. That matches the PR's "about 7 MB".
- #12 itself makes a full quota harmless. A failed save now rejects, the swap uses the lists in
  memory, and the popup says "Lists could not be saved …; they will download again next time."
  Without `unlimitedStorage`, the worst case is extra downloads, not wrong rules.
- With `unlimitedStorage` there is no ceiling. If a list keeps growing, nobody notices until
  storage use is large.
- If headroom becomes a problem later, there are ways that need no permission:
  - keep the list state in IndexedDB, which has the origin quota, not the 10 MiB cap;
  - or split `generalListRefresh` into one key per list, which also fixes the extra writes (see Risks).
- Older Chrome (before 114) had a 5 MiB quota. 6.87 MiB already fails there on main today. The
  manifest has no `minimum_chrome_version`.

### `alarms`: not needed

- `alarms` is used only for the 2-minute one-shot `listRefreshRetry` alarm, at most 3 tries per
  browser session.
- #12's first commit (`40756c9`, rebased as `c286278`) already makes a cut-off refresh resume:
  - each newly downloaded list is saved as it lands;
  - `lastRunAt` is written only at the end;
  - the next worker start retries, at most 3 times per session, and fetches only the missing lists.
- The only thing `alarms` adds is a sure wake 2 minutes later. Without it, the retry waits for the
  next worker wake: browser start, a popup action (switch, Allow, Update), or a storage write.
  - After #12, opening the popup no longer wakes the worker, so in practice the retry often waits
    for the next browser session.
  - Lists expire after 1 to 4 days, so a late retry costs little.
- Ways to do without it:
  1. **Accept the retry on next wake or next session.** This is commit 1's behaviour, and it is
     already much better than main, where a cut-off refresh loses every download and waits 12 h.
  2. **Stop Chrome killing the worker in the first place.**
     - According to Chrome's service-worker lifecycle docs, an idle worker is stopped after 30 s,
       and any extension API call resets that timer.
     - #12's per-list saves already call the storage API after each new download, so the worker is
       killed less often than on main.
     - What is left: one list whose main URL and mirrors take more than 30 s together with no API
       call in between. EasyList and EasyPrivacy have 4 URLs each, at up to 25 s each.
     - A cheap API call (e.g. `chrome.runtime.getPlatformInfo`) every ~20 s while a refresh runs
       would close that gap. Use a `setTimeout` chain, because the gate bans `setInterval`.
     - This needs checking in a real browser before relying on it.

| `test/no-background-fetch.test.js` "manifest has no background worker for list fetching" | "no alarms permission", "no unlimitedStorage for list caches" | Rewrites it to *require* both |
| `test/dnr.test.js` "permissions stay DNR + storage …" | permissions are exactly DNR + storage | Rewrites it |

policy is the owner's call. It shouldn't come in as a side effect of a speed PR.

## Risks (most serious first)

1. **Permission policy reversal.** See above. This needs the owner's decision.
2. **Many more storage writes in the worker.** Every `setState` reads and rewrites the whole
   `generalListRefresh` value, and #12 calls it after each new list. I measured with the same live
   lists:

   | Refresh | Main: calls / MiB rewritten | #12: calls / MiB rewritten |
   | --- | --- | --- |
   | First ever (empty state) | 4 / 11.9 | 11 / 42.2 |
   | With saved state, all 9 lists changed | 4 / 23.7 | 11 / 65.2 |

   - Each write also sends old and new values (~12 MiB) to the worker's own `storage.onChanged`
     listener (`src/general-background.js`). Pages no longer receive these, which is #12's big win.
     But the worker now does about 3× the work per refresh.
   - Storing one key per list (or saving after every few lists) would bring this down to roughly
     the size of the data that actually changed.
3. **The Twitch directory watcher may miss ad cards.** Not tested on the real site.
   - It now looks only at added nodes. Before, any page change triggered a full re-scan, so a
     feedback button that got its `aria-label` after insertion was still caught. Now it isn't: the
     observer only watches `childList`, not attributes.
   - A button whose card edge can't be found yet is given up after 10 tries. The tries are counted
     once per animation frame that follows a page change. On a busy page, 10 tries can go by in
     well under a second, before the grid has filled. Before, every page change re-checked it,
     with no limit.
   - The banner and `[aria-label="Advertisement"]` removal is safe: the injected CSS already hides
     both.
   - The 10-28 "Allow this page" session treated `src/twitch-directory-ads.js` as a locked file.
     No repo rule says so: worth confirming with the owner.
4. **Open pages don't hear about every change any more.**
   - If the popup is closed before Update finishes, `syncOpenPages()` never runs, and open pages
     keep their old hide rules until they reload.
   - The quiet background refresh never reaches open pages. The PR says so.
   - Low impact: hide rules only, until the next page load.
5. **Opening the popup no longer re-applies the rules.** That message was also an accidental
   repair step: opening the popup re-applied the blocking rules and the icon. Now a startup
   apply that went wrong stays wrong until a switch, Allow, Update or browser restart. Low.
6. **The `generalSync` broadcast** makes every frame of every tab re-read storage on each switch,
   Allow or Update.
   - Cheap now: `cosMeta` went from 185,794 bytes to 53 bytes, and 185,740 bytes moved to the
     worker-only `cosKeys`. That confirms the PR's "about 185 KB".
7. **Overlapping writes to the list state.** `setState` reads, changes and writes back in steps
   that can interleave. `applyEnabled`'s swap or fallback also writes `dynamicActive`.
   - More and longer writes during a refresh widen this existing window.
   - It corrects itself, because `refreshLists` runs `applyGeneralState` at the end. Low.
8. **The `cosKeys` change is one-way.** An older build loaded after this one looks for
   `cosMeta.keys`, finds nothing, and never deletes stale cosmetic keys. Very low.

The PR says its speed effects come from file sizes and code, not browser timings. My numbers above
are also byte counts, not timings.
